# Auto Job Applier — repository instructions

## Application execution (any harness)

- Recovery continues within the operator-selected overall application deadline. Settings defaults to 30 minutes, supports an adjustable duration and Off, and applies to new attempts. Supervision cancels the owned executor and cleans up at expiry; browser reloads, reconnects and same-dispatch replacement sessions do not reset that clock. Preserve submission evidence and record the timeout distinctly from a user stop. This operator-authorized deadline is separate from a helper's resumable call budget.

- Helpers assist the application executor; they do not bound its reasoning or decide that an application is over. Across every ATS, a helper miss, retry limit, unsupported control or expired call slice means inspect the evidence/options and try another supported approach in the same owned session. Keep moving toward submission; record recovery timing for later engineering. Finish blocked only for an evidenced unresolved obstacle after executor recovery, never merely because a helper returned `blocked` or `inspection_required`.
- When an expected control is missing, immediately take and visually inspect an owned-page screenshot, including embedded frames, overlays and inner scroll areas. Before ending an application for an unresolved obstacle, inspect a fresh screenshot and try the remaining plausible recovery. Capturing an image without reading it is not inspection. A user correction means continue; a CAPTCHA notice alone is not a challenge. This applies across every ATS and helper, without adding a separate approval or finish-permission gate.
- Read `skills/productivity/job-apply/SKILL.md`; for Workday also read `skills/productivity/workday-simplify/SKILL.md`.
- After the canonical startup instructions, launch immediately with `wait_seconds:0`; read ATS detail while the browser prepares, before form actions. Do not duplicate runtime preflight with repository exploration or doctor. For broken pages, use the shared reload/restart recovery and continue; unknown Simplify state or an earlier Submit click alone does not forbid recovery.
- These repository files are canonical. Hermes discovery is a thin entry point under `integrations/hermes_jobbot/skills/job-apply/`; other harnesses read the same canonical skills directly.
- Start through `jobbot start` or `python -m job_applier.application_runtime start <url>` using the selected private configuration and actual conversation ID. No API token, running dashboard or expiring browser lease is required locally. Never guess a database or dual-write history.
- Retry policy is shared by every portal: match the URL to the existing job, preserve earlier attempts, and start a fresh attempt for a new request unless successful submission is recorded. Failed, stopped, interrupted and submission-unknown history never require a special unblocker or proof of non-submission. Distinct requests may use distinct workspaces for the same posting/account; only explicit retry replaces its named session. Within an attempt, click history never disables edits, verification, answers or browser recovery. Follow current controls and actual confirmation evidence. Repeated calls within one request stay idempotent. See `docs/jobbot-v1/RETRY_POLICY.md` before changing this behavior.
- Use the repository virtualenv. `application_runtime doctor` is an optional read-only diagnostic; start performs configuration/history and real browser readiness checks automatically.
- Use `jobbot fast_forward` or `python -m job_applier.workday_fast session <session-id> --seconds 60` for Workday. Session-scoped calls resolve ownership and target. The CLI is harness-neutral and launches no model. Explicit HTTP accept/claim/advance is legacy compatibility only.
- Simplify fills; the harness handles exceptions. No in-run PDF extraction, resume hunts or reconstruction of career/education fields, on any ATS. Approved file upload remains allowed.
- Never edit helpers/skills during an application benchmark. Follow actual controls, preserve quiescence/ownership checks and verify submission once using the canonical skill's evidence policy; report the actual evidence source.

## Engineering

- Keep repository documentation current in the same change when behavior, dashboard pages, configuration, data ownership, integrations or operations change. Start with `docs/README.md` and the change-to-document map in `docs/DOCUMENTATION.md`; update the relevant guide and canonical reference rather than adding another conflicting workflow. Label historical evidence and proposals, preserve private data outside Git, and explain when a change has no documentation impact. This is an engineering maintenance practice, not an application-execution restriction or approval gate.
- For self-improvement reviews, follow `docs/jobbot-v1/SELF_IMPROVEMENT.md`. Give each run a persistent numbered/date label in commit subjects, an annotated Git tag and matching GitHub/Ubuntu run notes.
- Ask the user for explicit approval before adding any new application-execution restriction, refusal condition, retry limit, approval requirement or blocking rule in code, database constraints, helpers or executor instructions. Explain the concrete behavior it would prevent. Do not silently add such rules while fixing another problem; removal of an existing unnecessary veto does not require renewed approval.
- Read `docs/jobbot-v1/APPLICATION_RUNTIME.md` for helper responsibilities, shared versus Workday scope, and data ownership before adding another helper.
- Preserve dirty user changes. Never use live applications as fixtures or alter private production records to make tests pass.
- Add a focused failing regression, implement the bounded fix, then run the relevant tests and one final suite. Standard managed-suite command: `python -m pytest tests/jobbot_v1 -q`.
- Delegate routine test execution and validation to the existing authenticated Antigravity CLI (`agy`) with `gemini-3.8-flash-medium`. The primary engineering agent owns implementation changes and independently checks the reported logs/JUnit; an assigned validation worker should not delegate again or edit source unless explicitly asked.
- Commit each completed, validated engineering change as a local Git checkpoint before reporting completion. Do not leave completed changes awaiting a separate commit request; pushing still requires authorization.
- After a change is successfully tested, deploy it to the existing authoritative Ubuntu runtime as part of completion, without asking for deployment approval again. Preserve active applications, private configuration and unrelated changes; verify the deployed files and affected services before reporting completion. This standing deployment authorization does not authorize pushing to unrelated Git remotes.
- Keep profiles, credentials, databases, private screenshots/transcripts, lock/checkpoint files and node fixture dependencies out of Git. Use the ignored private artifacts area for deployment-specific configuration.
- Update the helper map when adding/removing a caller or helper. A new fast path does not prove older helpers unused.
